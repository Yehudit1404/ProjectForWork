**תוכן עניינים**

**1. רקע ומטרת הפרויקט**

**1.1 תיאור המשימה המקורית**

המשימה שהוגדרה: בניית אפליקציית SPA (Single Page
Application) של לוח מודעות, הכוללת מימוש מלא של כל פעולות ה-CRUD (יצירה,
קריאה, עדכון, מחיקה) מול REST API. האפליקציה מבוססת שני חלקים: שרת
(Server / API) הבנוי בטכנולוגיית C# החושף REST API ושומר את המודעות
בקובץ JSON מקומי, וקליינט (Client) הבנוי ב-Angular הצורך את ה-API. השראת
העיצוב היא לוח מודעות שכונתי בסגנון "What's Good in the Hood" — הצגת
מודעות ככרטיסיות בתוך רשת, מחולקות לפי קטגוריות, עם דגש על חיפוש וסינון
לפי מיקום גיאוגרפי.

**1.2 מטרות המסמך**

מסמך זה הינו אפיון מוצר מפורט (High-Level & Detailed
Functional Spec) המתאר במילים בלבד — ללא קוד — את כלל ההתנהגות, המסכים,
זרימות המשתמש, מבנה הנתונים, ממשקי ה-API והעיצוב הנדרשים למימוש הפרויקט
ברמה מקצועית, לצורך תכנון מדויק לפני תחילת הכתיבה בפועל.

**1.3 מטרות הפתרון**

- **הדגמת יכולת Full-Stack מקצה לקצה —** תכנון ובניית
  שרת REST API וקליינט SPA העובדים יחד בצורה חלקה ומאובטחת.

- **קוד איכותי ומאורגן —** הפרדת אחריות ברורה
  (Separation of Concerns), שכבות מוגדרות היטב בצד השרת והקליינט, שמות
  עקביים ומוסכמות קוד אחידות.

- **חוויית משתמש (UX) גבוהה —** ממשק נעים, אינטואיטיבי,
  מהיר, נגיש ורספונסיבי, התומך בעברית ו-RTL באופן מלא.

- **עמידה מלאה בדרישות —** מימוש כל דרישות הבסיס (CRUD,
  חיפוש, סינון) וכן מימוש מלא ואינטגרלי (לא כתוספת שולית) של דרישת
  הבונוס — שיוך מיקום גיאוגרפי למודעות באמצעות Google Maps וסינון לפי
  מיקום נוכחי.

- **מוכנות להערכה מקצועית —** תיעוד ברור, מבנה
  Repository מסודר ב-GitHub, קלות הרצה מקומית עבור בודק חיצוני.

**1.4 קהל היעד של המסמך**

מפתח/ת הפרויקט (עצמאי/ת), וכן גורם בודק/מעריך חיצוני
(למשל צוות טכני שמעריך את הפרויקט כמטלת בית / מטלת מיון). המסמך כתוב
ברמת פירוט המאפשרת מעבר ישיר לשלב התכנון הטכני והמימוש, ללא צורך בהחלטות
עיצוביות נוספות באמצע העבודה.

**2. סקירת ארכיטקטורה כללית**

**2.1 רכיבי המערכת**

המערכת בנויה משלושה רכיבים עיקריים הפועלים יחד:

- **Client — Angular SPA:** אפליקציית עמוד יחיד הרצה
  בדפדפן המשתמש. אחראית על כלל התצוגה, האינטראקציה, הניתוב הפנימי
  (Routing) והתקשורת מול ה-API בפרוטוקול HTTP/JSON.

- **Server — ASP.NET Core Web API (C#):** שרת REST חושף
  נקודות קצה (Endpoints) לביצוע כל פעולות ה-CRUD על מודעות, מבצע
  ולידציה, לוגיקה עסקית (כולל חישובי מרחק גיאוגרפי לצורך סינון לפי
  מיקום), ואחראי על קריאה/כתיבה לקובץ האחסון.

- **שכבת אחסון — קובץ ads.json:** קובץ JSON יחיד בצד
  השרת המשמש כ"מסד נתונים" פשוט לאחסון כלל המודעות. הגישה אליו מתבצעת אך
  ורק דרך שכבת ה-Repository בשרת, לעולם לא ישירות מהקליינט.

- **Google Maps Platform:** שירות חיצוני (Maps
  JavaScript API, Places API, Geocoding API) הנצרך ישירות מהקליינט להצגת
  מפות, חיפוש כתובות והמרת כתובת/קואורדינטות. תוצאת הבחירה (כתובת +
  קואורדינטות) נשלחת לשרת כחלק מנתוני המודעה ונשמרת יחד איתה.

**2.2 תרשים זרימת המידע (מילולי)**

הדפדפן (Angular App) שולח בקשות HTTP
(GET/POST/PUT/DELETE) בפורמט JSON אל ה-Web API. ה-API מעבד את הבקשה מול
שכבת השירות (Service Layer), אשר פונה לשכבת המאגר (Repository)
לקריאה/כתיבה מהקובץ ads.json בדיסק השרת, ומחזיר תשובה בפורמט JSON חזרה
לדפדפן. במקביל, כאשר המשתמש בוחר מיקום עבור מודעה או מבקש לסנן לפי מיקום
נוכחי, הדפדפן פונה ישירות לשירותי Google Maps (ולא דרך השרת) לצורך תצוגת
מפה, חיפוש כתובות (Autocomplete) והמרת קואורדינטות לכתובת קריאה (Reverse
Geocoding). רק הנתון הסופי — כתובת טקסטואלית וקואורדינטות (lat/lng) —
נשלח ונשמר בשרת כחלק מהמודעה.

**2.3 עקרונות ארכיטקטורה מנחים**

- הפרדה מלאה בין קליינט לשרת — תקשורת אך ורק דרך REST
  API מתועד, ללא תלות ישירה בין הטכנולוגיות.

- Stateless API — כל בקשה עצמאית ומכילה את כל המידע
  הדרוש לעיבודה (לרבות זהות המשתמש היוצר, ראו סעיף 4.9).

- שכבתיות בצד השרת (Controller → Service → Repository)
  המאפשרת בעתיד להחליף את שכבת האחסון (למשל ממעבר מ-JSON למסד נתונים
  אמיתי) מבלי לשנות את שכבת הלוגיקה העסקית או ה-API החיצוני.

- שכבתיות בצד הקליינט (Core / Shared / Features) המאפשרת
  שימוש חוזר ברכיבים ותחזוקה נוחה.

- עיצוב Responsive-First ו-RTL-First — כל רכיב מתוכנן
  מלכתחילה לעברית ולתצוגה נכונה בכל גודל מסך.

**3. מודל הנתונים — ישות "מודעה" (Ad)**

נשמר ב-ads.json ומוחזר ב-JSON) לבין המודלים בצד הקליינט.

**4. אפיון ה-Backend (Server) — C# / ASP.NET Core Web
API**

**4.1 טכנולוגיה וסביבת פיתוח**

- פלטפורמה: ASP.NET Core Web API (גרסה עדכנית, .NET 8),
  בשפת C#.

- תבנית ארכיטקטונית: Controller → Service → Repository,
  עם הזרקת תלויות (Dependency Injection) מובנית של ASP.NET Core.

- סריאליזציה: System.Text.Json, כולל הגדרת מדיניות שמות
  שדות אחידה (camelCase) כך שתואמת למוסכמות הצד של הקליינט
  ב-Angular/TypeScript.

- תיעוד API: Swagger / OpenAPI (Swashbuckle) — חשיפת
  ממשק בדיקה אינטראקטיבי בסביבת הפיתוח, מאפשר לבודק חיצוני לבחון את
  ה-API ללא צורך בהרצת הקליינט.

- CORS: מדיניות CORS מוגדרת במפורש כדי לאפשר קריאות
  מהכתובת בה רץ הקליינט (למשל בסביבת הפיתוח:
  http://localhost:4200).

**4.2 מבנה תיקיות מוצע לפרויקט השרת**

להלן מבנה תיקיות מוצע (תיאור מילולי של החלוקה, לא
קוד):

- **Controllers —** מכיל את AdsController, האחראי אך ורק
  על קבלת בקשות HTTP, אימות קלט בסיסי והחזרת תשובות; אינו מכיל לוגיקה
  עסקית.

- **Models —** מכיל את מודל הישות הפנימי (Ad) ואת
  אובייקטי ההעברה (DTOs) הנפרדים לבקשות יצירה ועדכון (CreateAdRequest,
  UpdateAdRequest) ולתשובה (AdResponse), כדי שלא לחשוף בטעות שדות
  פנימיים.

- **Services —** מכיל את IAdService/AdService — הלוגיקה
  העסקית: ולידציה עסקית, בדיקת בעלות (Owner) לפני עדכון/מחיקה, חישוב
  מרחק גיאוגרפי (Haversine) לצורך סינון וסידור לפי מיקום, מיון ועימוד
  תוצאות.

- **Repositories / Data —** מכיל את
  IAdRepository/JsonAdRepository — האחראי הבלעדי על קריאה וכתיבה לקובץ
  ads.json, כולל נעילה (Locking) למניעת כתיבה בו-זמנית פוגענית (ראו סעיף
  4.5).

- **wwwroot/Data (או תיקייה ייעודית) —** מיקום קובץ
  ads.json בפועל בדיסק השרת, וכן קובץ seed (נתוני דוגמה) לטעינה ראשונית
  אם הקובץ אינו קיים.

- **Program.cs —** נקודת הכניסה של השרת: רישום שירותים
  ל-DI, הגדרת CORS, Swagger, Middleware לטיפול בשגיאות (ראו 4.7).

**4.3 נקודות קצה (REST API Endpoints)**

להלן מפרט מלא של כלל נקודות הקצה שהשרת חושף. כל הבקשות
והתשובות בפורמט JSON.

| **פעולה (Method)** | **נתיב (Route)** | **תיאור**                                                                                           | **קוד תשובה עיקרי**                            |
|-------------------------------------------|-----------------------------------------|----------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------|
| GET                | /api/ads         | החזרת רשימת מודעות, עם פרמטרים אופציונליים לסינון וחיפוש (ראו 4.4).                                 | 200 OK                                         |
| GET                | /api/ads/{id}    | החזרת מודעה בודדת לפי מזהה.                                                                         | 200 OK / 404 Not Found                         |
| POST               | /api/ads         | יצירת מודעה חדשה. גוף הבקשה כולל את כל שדות המודעה (למעט id/createdAt/updatedAt, שנקבעים בשרת).     | 201 Created                                    |
| PUT                | /api/ads/{id}    | עדכון מודעה קיימת. מתבצע רק אם מזהה הבעלים בבקשה תואם את בעלי המודעה.                               | 200 OK / 403 Forbidden / 404 Not Found         |
| DELETE             | /api/ads/{id}    | מחיקת מודעה קיימת. מתבצע רק אם מזהה הבעלים בבקשה תואם את בעלי המודעה.                               | 204 No Content / 403 Forbidden / 404 Not Found |
| GET                | /api/categories  | החזרת רשימת הקטגוריות הקבועות הנתמכות במערכת (כולל שם וצבע), לשימוש הקליינט בבניית מסננים ותפריטים. | 200 OK                                         |

**4.4 פרמטרים לסינון וחיפוש (GET /api/ads)**

נקודת הקצה לקבלת רשימת מודעות תומכת בפרמטרים הבאים בשורת
הכתובת (Query String), הניתנים לשילוב זה עם זה (חיבור לוגי
"וגם"):

| **פרמטר**      | **טיפוס**         | **תיאור**                                                                                             |
|---------------------------------------|------------------------------------------|------------------------------------------------------------------------------------------------------------------------------|
| search         | מחרוזת            | חיפוש טקסט חופשי בשדות הכותרת והתיאור (ללא תלות רישיות).                                              |
| category       | מחרוזת            | סינון לפי קטגוריה בודדת מתוך הרשימה הסגורה.                                                           |
| ownerId        | מזהה              | סינון להצגת מודעות של בעלים מסוים בלבד (משמש למסך "המודעות שלי").                                     |
| lat, lng       | מספר עשרוני (זוג) | קואורדינטות מיקום ייחוס — נדרש לצורך חישוב מרחק וסינון גיאוגרפי (בונוס).                              |
| radiusKm       | מספר              | רדיוס בק"מ סביב מיקום הייחוס; מודעות ללא מיקום שמור, או מחוץ לרדיוס, אינן מוחזרות כאשר פרמטר זה נשלח. |
| sortBy         | מחרוזת (enum)     | מפתח מיון: newest (ברירת מחדל, החדשות ראשונות), distance (הקרובות ראשונות — תקף רק כשנשלחו lat/lng).  |
| page, pageSize | מספר שלם          | עימוד תוצאות (Pagination) לביצועים טובים גם עם מספר רב של מודעות.                                     |

**4.5 מנגנון האחסון — קובץ ads.json**

כל המודעות נשמרות במבנה מערך JSON יחיד בתוך קובץ אחד
בשרת. שכבת ה-Repository היא הגורם היחיד המורשה לקרוא ולכתוב לקובץ
זה.

- **טעינה ראשונית (Seed):** אם הקובץ אינו קיים בהפעלה
  הראשונה של השרת, הוא נוצר אוטומטית עם כ-6–8 מודעות דוגמה, הפרושות על
  פני כל הקטגוריות, כדי שהאפליקציה תוצג עם תוכן משמעותי מיד עם ההרצה
  הראשונה (לרבות מיקומים לדוגמה כדי להדגים את פיצ'ר הבונוס).

- **עקביות ומניעת כתיבה מקבילה:** מאחר שמדובר בקובץ ולא
  במסד נתונים אמיתי, כל פעולת כתיבה (יצירה/עדכון/מחיקה) מבוצעת בתוך
  נעילה (Lock) יחידה בתהליך השרת, כך שבקשות מקבילות לא יגרמו לשחיתות
  הקובץ. הקריאה מהקובץ מתבצעת בתחילת כל בקשה (ללא שכבת Cache קבועה
  בזיכרון), כדי להבטיח שהנתונים תמיד עדכניים — עם אפשרות עתידית
  לאופטימיזציה באמצעות Caching בזיכרון עם רענון בכל כתיבה.

- **תמונות:** התמונה נשמרת כמחרוזת Base64 בתוך רשומת
  המודעה עצמה בקובץ ה-JSON (ולא כקובץ נפרד), כדי לשמור על פשטות הפתרון
  התואמת לדרישה של "קובץ JSON מקומי". בצד הקליינט תיושם הגבלת גודל קובץ
  (עד 2MB) ודחיסה/הקטנה (Resize) לפני ההעלאה, כדי לשמור על גודל קובץ
  ads.json סביר.

- **גיבוי לוגי:** בכל כתיבה מוצלחת, ניתן (כשיפור עתידי)
  לשמור עותק גיבוי של הקובץ הקודם, למניעת אובדן מידע במקרה קיצון.

**4.6 ולידציה וכללי עסקיים**

- שדות חובה (title, description, category, ownerId,
  ownerName) נבדקים הן בצד הקליינט (למניעת שליחה מיותרת) והן בצד השרת
  (כמקור אמת אחרון ובלתי תלוי בקליינט).

- אורכי טקסט מקסימליים/מינימליים נאכפים בשרת (title עד
  80 תווים, description עד 1000 תווים).

- שדה price, כאשר נשלח, חייב להיות מספר חיובי.

- קטגוריה חייבת להיות אחת מהרשימה הסגורה המוגדרת בשרת —
  בקשה עם קטגוריה לא מוכרת נדחית.

- בעת עדכון (PUT) או מחיקה (DELETE), השרת בודק
  שה-ownerId שנשלח בבקשה זהה ל-ownerId השמור על גבי המודעה; אחרת מוחזר
  קוד 403 Forbidden ואין ביצוע הפעולה.

- בקשה שלא עוברת ולידציה מחזירה קוד 400 Bad Request עם
  מבנה שגיאה אחיד (ראו 4.7), הכולל רשימת שדות שגויים והודעה
  מובנת.

**4.7 טיפול בשגיאות**

השרת כולל שכבת Middleware גלובלית לטיפול בשגיאות בלתי
צפויות (Exceptions), כך שכל שגיאה — צפויה או לא — מוחזרת ללקוח במבנה
אחיד וברור (קוד שגיאה, הודעה קריאה לאדם, ולעיתים רשימת פרטים לפי שדה),
ולעולם לא כ-Stack Trace גולמי. כל שגיאה מתועדת (Logging) בצד השרת לצורכי
דיבוג.

| **קוד HTTP**              | **מתי מוחזר**                                                 |
|--------------------------------------------------|--------------------------------------------------------------------------------------|
| 400 Bad Request           | קלט לא תקין — שדה חובה חסר, ערך מחוץ לטווח, קטגוריה לא מוכרת. |
| 403 Forbidden             | ניסיון לעדכן/למחוק מודעה שאינה בבעלות מזהה המבקש.             |
| 404 Not Found             | בקשה למודעה עם מזהה שאינו קיים.                               |
| 500 Internal Server Error | שגיאה בלתי צפויה בצד השרת (למשל כשל בגישה לקובץ).             |

**4.8 מנגנון "בעלות" (Ownership) ללא התחברות
מלאה**

מאחר שהאפיון המקורי אינו דורש מנגנון הרשמה/התחברות עם
סיסמה, אך כן דורש הבחנה בין "מודעות שהמשתמש יצר" לבין מודעות אחרות,
מתוכנן מנגנון זהות קליינטית קלה (Lightweight Client Identity):

**1.** בכניסה הראשונה של המשתמש לאפליקציה, נוצר בדפדפן
מזהה ייחודי (ownerId, מסוג GUID) הנשמר באחסון המקומי של הדפדפן
(localStorage), ונשמר לצמיתות עד שהמשתמש מנקה אותו במפורש.

**2.** בפעם הראשונה מוצגת למשתמש בקשה קצרה וידידותית
לבחירת שם תצוגה (ownerName), הנשמר גם הוא ב-localStorage לצד
המזהה.

**3.** כל בקשת יצירה, עדכון או מחיקה הנשלחת מהקליינט
לשרת כוללת את ה-ownerId (בגוף הבקשה ביצירה, ובכותרת ייעודית X-Owner-Id
בעדכון/מחיקה).

**4.** השרת שומר את ownerId ו-ownerName כחלק מרשומת
המודעה בעת יצירתה, ומאפשר עדכון/מחיקה רק כאשר ownerId המצורף לבקשה תואם
לזה השמור על המודעה.

**5.** בצד הממשק, כפתורי "עריכה" ו"מחיקה" מוצגים אך ורק
על מודעות שה-ownerId שלהן תואם למזהה המקומי הנוכחי — כך שמבחינת המשתמש
החוויה מקבילה להתחברות רגילה, ללא הצורך במימוש שכבת אימות מלאה.

> **הערה:** מגבלה מודעת: זהו מנגנון "בעלות" נוח לצרכי
> הפרויקט ואינו מנגנון אבטחה קשיח (משתמש טכני יכול תיאורטית לשלוח
> ownerId שאינו שלו). מאחר שהמשימה אינה כוללת דרישת אימות/הרשאות, זהו
> איזון סביר בין פשטות למימוש הדרישה הפונקציונלית "מודעות שאני יצרתי".
> אם בעתיד תידרש הרשמה/התחברות אמיתית, שכבת ה-Service בשרת כבר בנויה כך
> שניתן להחליף את בדיקת ה-ownerId בבדיקת משתמש מאומת (JWT) ללא שינוי
> במבנה ה-API החיצוני.

**4.9 חישוב מרחק גיאוגרפי לצורך סינון לפי מיקום
(בונוס)**

כאשר מתקבלת בקשת GET /api/ads עם פרמטרים lat, lng,
ו-radiusKm, שכבת השירות בשרת מחשבת עבור כל מודעה שיש לה location שמור את
המרחק הקווי ("מעוף הציפור") בין נקודת הייחוס לבין מיקום המודעה, באמצעות
נוסחת Haversine הסטנדרטית לחישוב מרחק בין שתי נקודות על פני כדור הארץ.
מודעות שהמרחק המחושב שלהן חורג מ-radiusKm, וכן מודעות ללא מיקום שמור
כלל, מוסרות מהתוצאה. אם התבקש sortBy=distance, התוצאה ממוינת מהקרוב
לרחוק, וכל מודעה מוחזרת עם שדה נוסף distanceKm המציין את מרחקה המדויק —
שדה זה משמש להצגת התג "X ק״מ ממך" על גבי הכרטיס בצד הקליינט.

**5. אפיון ה-Client (Angular)**

**5.1 טכנולוגיה וכלים**

- Angular (גרסה עדכנית), עם רכיבי Standalone Components
  וניתוב מבוסס Angular Router.

- Angular Material + Angular CDK — לפי בחירת הלקוח,
  ספריית ה-UI הראשית של הפרויקט (כפתורים, שדות טופס, כרטיסים, דיאלוגים,
  צ'יפים, סליידרים, אייקונים).

- @angular/google-maps — ספריית האינטגרציה הרשמית של
  Angular עבור Google Maps JavaScript API, לשילוב מפה, סמנים (Markers)
  ו-Autocomplete.

- RxJS — לניהול זרמי נתונים אסינכרוניים (חיפוש עם
  Debounce, שילוב מספר מסננים בו-זמנית).

- Reactive Forms — לבניית טופס יצירה/עריכת מודעה עם
  ולידציה חכמה מבוססת מצב.

- Angular Signals — לניהול מצבי טעינה/שגיאה פשוטים ברמת
  הרכיב.

**5.2 מבנה תיקיות ומודולים מוצע**

- **Core —** שירותים גלובליים החיים לאורך כל חיי
  האפליקציה: שירות תקשורת עם ה-API (AdService), שירות זהות משתמש
  (IdentityService), שירות מיקום נוכחי (GeolocationService), שירות
  קטגוריות (CategoryService), וכן Interceptor שמצרף אוטומטית את מזהה
  הבעלים לכל בקשה יוצאת, ו-Interceptor לטיפול אחיד בשגיאות HTTP.

- **Shared —** רכיבי UI ניתנים לשימוש חוזר: כרטיס מודעה
  (AdCard), תגית קטגוריה צבעונית (CategoryBadge), דיאלוג אישור פעולה
  (ConfirmDialog), מצב טעינה (LoadingSkeleton), מצב ריק
  (EmptyState).

- **Features/Board —** מסך הלוח הראשי: רשימת מודעות, שדה
  חיפוש, מסנני קטגוריה ומיקום.

- **Features/AdDetail —** מסך פרטי מודעה בודדת.

- **Features/AdForm —** מסך יצירה/עריכה של מודעה, כולל
  רכיב בחירת מיקום על גבי מפה.

- **Features/MyAds —** מסך "המודעות שלי".

**5.4 שירותים מרכזיים בצד הקליינט**

- **AdService —** מרכז את כל התקשורת מול /api/ads: שליפת
  רשימה (עם פרמטרי סינון), שליפת מודעה בודדת, יצירה, עדכון ומחיקה. זהו
  נקודת הגישה היחידה לנתוני מודעות עבור שאר האפליקציה.

- **IdentityService —** אחראי על יצירה/קריאה/עדכון של
  ownerId ו-ownerName באחסון המקומי, וחושף פונקציית עזר isOwner(ad)
  המשמשת בכל מקום להחלטה האם להציג כפתורי עריכה/מחיקה.

- **GeolocationService —** עוטף את ה-Geolocation API של
  הדפדפן, מטפל בבקשת הרשאה, במקרה של סירוב/שגיאה ומחזיר מיקום נוכחי
  (lat/lng) לשימוש הן במסך הלוח (סינון) והן במסך הטופס ("השתמש במיקום
  שלי").

- **MapsService —** עוטף את הטעינה של Google Maps
  JavaScript API, כולל Autocomplete לחיפוש כתובות ו-Reverse Geocoding
  (המרת קואורדינטות לכתובת קריאה).

- **CategoryService —** מחזיק את רשימת הקטגוריות (נטענת
  מ-/api/categories) יחד עם צבע ואייקון לכל קטגוריה, לשימוש עקבי בכל
  רכיבי התצוגה.

**5.5 ניהול מצב (State Management)**

בהתחשב בהיקף האפליקציה, לא נדרשת ספריית ניהול מצב
חיצונית (כגון NgRx). ניהול המצב מתבצע ברמת שירות (Service-based State)
באמצעות RxJS ו-Signals: שירות הלוח מחזיק Observable/Signal של רשימת
המודעות הנוכחית ומצב המסננים הפעילים, כל שינוי במסנן (חיפוש, קטגוריה,
מיקום) מפעיל מחדש בקשה מסוננת לשרת. מצבי טעינה (loading) ושגיאה (error)
מנוהלים ברמת כל מסך באמצעות Signals ומוצגים ב-UI בהתאם (שלד טעינה /
הודעת שגיאה ידידותית).

**5.6 Interceptor לצירוף זהות ולתקשורת HTTP**

כלל הבקשות היוצאות מהקליינט אל ה-API עוברות דרך
Interceptor מרכזי המצרף אוטומטית את מזהה הבעלים הנוכחי (כותרת
X-Owner-Id, ובבקשות POST/PUT גם בתוך גוף הבקשה), כך ששאר הקוד באפליקציה
אינו צריך לדעת על פרט מימוש זה. Interceptor נוסף אחראי לתפיסת שגיאות
HTTP ברמה גלובלית והצגתן כהודעת Snackbar אחידה למשתמש.

**6. מסכי המערכת ועיצוב מפורט**

סעיף זה מתאר במדויק, מסך אחר מסך, את מבנה התצוגה,
האלמנטים המוצגים וסדר הופעתם מלמעלה למטה, כהכנה ישירה לשלב העיצוב הגרפי
(Wireframing) והמימוש.

**6.1 מסך ראשי — לוח המודעות (Board)**

המסך המרכזי של האפליקציה, המוצג מיד בכניסה. בנוי מלמעלה
למטה מהאזורים הבאים:

**1.** סרגל עליון (Header): בצד ימין (תחילת השורה ב-RTL)
— שם/לוגו האפליקציה. בצד שמאל — אווטאר עגול עם ראשי התיבות של שם המשתמש
הנוכחי (עם תפריט נפתח: "שנה שם תצוגה", "נקה נתונים מקומיים"), כפתור
"המודעות שלי", וכפתור בולט וצבעוני "+ מודעה חדשה" (כפתור מסוג Raised
Button בצבע accent, בדומה לכפתור ה-GO הכתום בתמונת ההשראה).

**2.** אזור עליון (Hero): כותרת קצרה ותמציתית של
האפליקציה ותת-כותרת, ומתחתיה שדה חיפוש גדול ובולט על כל רוחב האזור, עם
אייקון זכוכית מגדילה, Placeholder בנוסח "חפשו מודעות לפי כותרת או
תיאור..." וכפתור ניקוי (X) כשיש טקסט. החיפוש פועל בזמן אמת עם השהיה קלה
(Debounce) כדי לא להציף את השרת בבקשות.

**3.** שורת מסנני קטגוריה: קבוצת תגיות לחיצות (Chips)
אופקית — "הכל" ולצידה כל קטגוריה, כל תגית בצבע הקטגוריה שלה (ראו טבלת
3.2). לחיצה על תגית מסננת את הרשימה בהתאם; ניתן לבחור קטגוריה אחת בכל
רגע נתון (או "הכל").

**4.** שורת סינון מיקום (בונוס): כפתור "מודעות בקרבתי"
עם אייקון מיקום. בלחיצה ראשונה מתבקשת הרשאת מיקום מהדפדפן. עם קבלת
ההרשאה, נחשף Slider לבחירת רדיוס חיפוש (טווח 1–50 ק״מ, ברירת מחדל 10
ק״מ) ומתג (Toggle) "מיין לפי מרחק". אם ההרשאה נדחתה, מוצגת הודעה
ידידותית המסבירה כיצד לאפשר גישה למיקום מהגדרות הדפדפן, מבלי לחסום את
שאר השימוש באפליקציה.

**5.** רשת המודעות (Ads Grid): רשת רספונסיבית של כרטיסי
מודעה (ראו 6.2) — 4 עמודות במסך רחב (Desktop), 2 עמודות בטאבלט, עמודה
אחת במובייל. המודעות ממוינות כברירת מחדל מהחדשה לישנה, ולפי מרחק כאשר
מופעל מיון לפי מיקום.

**6.** עימוד (Pagination): בתחתית הרשת — בקרת עימוד
(מספרי עמודים / "טען עוד") להצגת תוצאות רבות מבלי לפגוע בביצועים.

**7.** מצב ריק (Empty State): כאשר החיפוש/הסינון אינו
מחזיר תוצאות — איור/אייקון ניטרלי, טקסט "לא נמצאו מודעות התואמות לחיפוש
שלך" וכפתור "נקה מסננים".

**8.** מצב טעינה (Loading State): בעת הטעינה הראשונית או
רענון תוצאות — כרטיסי שלד (Skeleton Cards) המדמים את מבנה כרטיס המודעה,
למניעת "קפיצה" חזותית כשהתוכן נטען.

**6.2 כרטיס מודעה (Ad Card) — עיצוב מפורט**

היחידה החזותית המרכזית באפליקציה, המופיעה ברשת הראשית,
במסך "המודעות שלי" ובתוצאות סינון מיקום. מבנה הכרטיס מלמעלה למטה:

- פס צבע דק (בגובה כ-4 פיקסלים) בראש הכרטיס, בצבע
  הקטגוריה — רמז חזותי מהיר לסוג המודעה עוד לפני קריאת הטקסט.

- תמונה: אם קיימת תמונה למודעה, היא מוצגת ביחס גובה-רוחב
  קבוע (לדוגמה 4:3) בראש הכרטיס; אם אין תמונה, מוצג רקע ניטרלי עם אייקון
  קטגוריה גדול במרכז.

- שורת מטא עליונה: תגית קטגוריה קטנה וצבעונית מצד אחד,
  ותאריך פרסום יחסי ("לפני יומיים") מהצד השני.

- כותרת המודעה: טקסט מודגש, שורה או שתיים לכל היותר עם
  קיצור (Ellipsis) אם ארוכה מדי.

- תיאור מקוצר: עד שתי שורות טקסט עם קיצור בסוף, נותן
  טעימה מתוכן המודעה.

- שורה תחתונה: מחיר בולט (אם רלוונטי לקטגוריה) בצד אחד,
  ובצד השני — שם המפרסם, ובמידה והופעל סינון מיקום — תגית קטנה "X.X ק״מ
  ממך".

- אינטראקציה: ריחוף (Hover) בדסקטופ מציג הצללה עדינה
  והגדלה קלה של הכרטיס (אפקט Scale עדין); לחיצה בכל מקום על הכרטיס
  מנווטת לעמוד פרטי המודעה.

- פעולות בעלים: אם המודעה שייכת למשתמש הנוכחי, מופיעים
  בפינת הכרטיס שני אייקוני פעולה קטנים — עריכה (עיפרון) ומחיקה (פח אשפה)
  — הנעצרים (Stop Propagation) מבלי לגרום לניווט לעמוד הפרטים.

**6.3 עמוד פרטי מודעה (Ad Detail)**

**1.** שביל ניווט עליון (Breadcrumb): "לוח מודעות ← \[שם
הקטגוריה\] ← \[כותרת המודעה\]", המאפשר חזרה מהירה.

**2.** תמונה ראשית גדולה בראש העמוד (אם קיימת), בפריסה
רחבה.

**3.** כותרת המודעה בגודל בולט, ולצידה תגית הקטגוריה
הצבעונית.

**4.** מחיר (אם רלוונטי) מוצג בבליטות גבוהה מיד מתחת
לכותרת.

**5.** תיאור מלא של המודעה, ללא קיצור, בפסקה קריאה עם
רווחים בין שורות.

**6.** אזור פרטי מפרסם: שם המפרסם ותאריך הפרסום/עדכון
האחרון.

**7.** אזור מיקום (אם קיים למודעה): מפת Google Maps
מוטמעת בגודל בינוני עם סמן (Marker) במיקום המדויק, ומתחתיה הכתובת הקריאה
כטקסט. אם למודעה אין מיקום, אזור זה אינו מוצג כלל.

**8.** שורת פעולות תחתונה: אם המשתמש הנוכחי הוא בעל
המודעה — כפתורי "ערוך מודעה" ו"מחק מודעה" (הכפתור השני בצבע אזהרה); אחרת
אינם מוצגים כלל.

**6.4 טופס יצירה/עריכה של מודעה (Ad Form)**

טופס יחיד המשמש הן ליצירת מודעה חדשה והן לעריכת מודעה
קיימת (במצב עריכה השדות מגיעים ממולאים מראש). מחולק לשלושה אזורים
ברורים:

**א. פרטים בסיסיים**

- שדה "כותרת" — שדה טקסט חד-שורתי עם מונה תווים חי
  (0/80) ואינדיקציה ויזואלית כשמתקרבים למגבלה.

- שדה "תיאור" — אזור טקסט רב-שורתי הניתן להרחבה, עם מונה
  תווים (0/1000).

- שדה "קטגוריה" — רשימה נפתחת (Select) עם אייקון וצבע
  לכל קטגוריה, בחירה יחידה וחובה.

- שדה "מחיר" — שדה מספרי, מוצג/מושבת אוטומטית בהתאם
  לרלוונטיות הקטגוריה שנבחרה (ראו טבלת 3.2).

**ב. תמונה**

- אזור גרירה-ושחרור (Drag & Drop) עם אפשרות לחיצה לבחירת
  קובץ מהמכשיר, מציג הנחיות פורמט וגודל מקסימלי (עד 2MB).

- תצוגה מקדימה (Preview) מיידית של התמונה שנבחרה, עם
  כפתור "הסר תמונה".

- במקרה של קובץ גדול מדי — הודעת שגיאה ברורה והצעה
  לדחוס/לבחור תמונה אחרת (הקטנת התמונה בצד הלקוח לפני השליחה, כדי לשמור
  על גודל סביר בקובץ הנתונים).

**ג. מיקום (בונוס — משולב באופן מלא בטופס)**

- שדה חיפוש כתובת עם השלמה אוטומטית (Google Places
  Autocomplete) — המשתמש מתחיל להקליד כתובת ובוחר מתוך הצעות.

- מפה אינטראקטיבית המוצגת מתחת לשדה החיפוש, עם סמן
  (Marker) הניתן לגרירה ידנית לכיוונון מדויק של המיקום.

- כפתור "השתמש במיקום הנוכחי שלי" — מפעיל את שירות
  המיקום של הדפדפן וממקם את הסמן במיקום המשתמש בפועל.

- לאחר בחירת מיקום (בכל אחת מהדרכים), מוצגת מתחת למפה
  הכתובת הקריאה שחושבה אוטומטית (Reverse Geocoding).

- שדה המיקום הוא אופציונלי — ניתן לשמור מודעה ללא מיקום
  כלל; עם זאת מוצגת המלצה עדינה (טקסט מנחה) לצרף מיקום כדי שהמודעה תופיע
  גם בחיפושי "מודעות בקרבתי" של משתמשים אחרים.

**ד. פעולות טופס**

- כפתור "שמור מודעה" (ביצירה) / "עדכן מודעה" (בעריכה) —
  מושבת כל עוד הטופס אינו תקין, עם סימון ברור של השדות השגויים.

- כפתור "ביטול" — חוזר למסך הקודם; אם קיימים שינויים שלא
  נשמרו, מוצג דיאלוג אישור "לצאת בלי לשמור?" למניעת אובדן מידע
  בטעות.

- בשמירה מוצלחת — הודעת הצלחה קצרה (Snackbar) וניווט
  אוטומטי לעמוד פרטי המודעה שנוצרה/עודכנה. בכישלון — הודעת שגיאה ברורה
  עם אפשרות לנסות שוב.

**6.5 מחיקת מודעה — דיאלוג אישור**

לחיצה על כפתור המחיקה (מהכרטיס או מעמוד הפרטים) פותחת
תמיד דיאלוג אישור (Modal) — לעולם לא מחיקה מיידית ללא אישור. הדיאלוג
מציג את כותרת המודעה למחיקה, טקסט אזהרה "פעולה זו אינה הפיכה", וכפתורי
"מחק" (בצבע אזהרה בולט) ו"ביטול". לאחר מחיקה מוצלחת — הודעת Snackbar
ועדכון מיידי של הרשימה המוצגת ללא צורך ברענון העמוד.

**6.6 מסך "המודעות שלי" (My Ads)**

מסך זהה במבנהו למסך הלוח הראשי (חיפוש, רשת כרטיסים), אך
מסונן תמיד למודעות שה-ownerId שלהן תואם למשתמש הנוכחי בלבד. בכל כרטיס
במסך זה מוצגים תמיד כפתורי עריכה ומחיקה (ללא צורך בבדיקת בעלות נוספת,
שכן כל המוצג שייך למשתמש). כאשר למשתמש אין עדיין מודעות משלו, מוצג מצב
ריק ייעודי: איור, טקסט "עדיין לא פרסמת אף מודעה" וכפתור בולט "פרסם את
המודעה הראשונה שלך" המוביל ישירות לטופס היצירה.

**6.7 ניהול זהות משתמש (Onboarding קל)**

בכניסה הראשונה אי-פעם לאפליקציה (כלומר כשלא קיים עדיין
ownerId מקומי), מוצג דיאלוג פתיחה קצר וידידותי: "ברוכים הבאים ללוח
המודעות! איך נקרא לך?" עם שדה טקסט לשם תצוגה וכפתור "התחל/י". לאחר
מילוי, הדיאלוג אינו מוצג שוב, אלא אם המשתמש בוחר לאפס את הנתונים
המקומיים מתוך תפריט המשתמש בסרגל העליון. אפשרות "שינוי שם תצוגה" זמינה
תמיד מאותו תפריט.

**7. זרימות משתמש עיקריות (User Flows)**

**7.1 זרימה א׳ — צפייה, חיפוש וסינון מודעות**

**1.** המשתמש נכנס לאפליקציה — מוצג לוח המודעות עם כלל
המודעות, ממוינות מהחדשה לישנה.

**2.** המשתמש מקליד מילת חיפוש בשדה החיפוש — לאחר השהיה
קצרה, הרשימה מתעדכנת אוטומטית להצגת מודעות תואמות בלבד.

**3.** המשתמש בוחר קטגוריה מתוך שורת התגיות — הרשימה
מתעדכנת להצגת מודעות מהקטגוריה שנבחרה בלבד (בשילוב עם מילת החיפוש, אם
קיימת).

**4.** המשתמש לוחץ "מודעות בקרבתי" — הדפדפן מבקש הרשאת
מיקום. עם אישור, מוצג סליידר רדיוס; הרשימה מתעדכנת להצגת מודעות בטווח
שנבחר בלבד, עם תג מרחק על כל כרטיס, וניתן להפעיל מיון לפי מרחק.

**5.** המשתמש לוחץ על כרטיס מודעה — מנווט לעמוד פרטי
המודעה המלא.

**7.2 זרימה ב׳ — יצירת מודעה חדשה (כולל מיקום)**

**1.** המשתמש לוחץ על כפתור "+ מודעה חדשה" מהסרגל
העליון.

**2.** אם זו הכניסה הראשונה שלו לאפליקציה, מתבקש תחילה
להזין שם תצוגה (ראו 6.7).

**3.** נפתח טופס יצירת מודעה ריק — המשתמש ממלא כותרת,
תיאור ובוחר קטגוריה.

**4.** אם הקטגוריה תומכת במחיר, המשתמש ממלא גם שדה
מחיר.

**5.** המשתמש מעלה תמונה (אופציונלי) וצופה בתצוגה
המקדימה.

**6.** המשתמש מזין כתובת בשדה המיקום ובוחר מתוך ההשלמה
האוטומטית, או גורר את הסמן על המפה, או לוחץ "השתמש במיקום שלי"
(אופציונלי).

**7.** המשתמש לוחץ "שמור מודעה" — הטופס מוולד; אם תקין,
נשלחת בקשת יצירה לשרת.

**8.** בהצלחה: הודעת אישור קצרה ומעבר אוטומטי לעמוד פרטי
המודעה החדשה, שם המודעה מוצגת בדיוק כפי שתופיע לכל משתמש אחר, כולל המפה
שנבחרה.

**7.3 זרימה ג׳ — עריכה ומחיקה של מודעה קיימת**

**1.** המשתמש רואה כפתורי עריכה/מחיקה על כרטיס מודעה או
בעמוד פרטים — אך ורק על מודעות שיצר בעצמו.

**2.** עריכה: נפתח אותו טופס כמו ביצירה, ממולא מראש
בנתוני המודעה הקיימת (כולל מיקום קיים, אם יש); לאחר שינוי ולחיצה על
"עדכן מודעה", נשלחת בקשת עדכון לשרת ומוצגים הנתונים המעודכנים.

**3.** מחיקה: נפתח דיאלוג אישור עם שם המודעה; אישור שולח
בקשת מחיקה לשרת, המודעה מוסרת מיידית מכל התצוגות, ומוצגת הודעת
אישור.

**4.** ניסיון גישה לעריכה/מחיקה של מודעה שאינה בבעלות
המשתמש (למשל דרך קישור ישיר) — נחסם בצד הקליינט ומוצג הודעה מתאימה; השרת
חוסם זאת ממילא ברמת ה-API (הגנת עומק-כפולה, Defense in Depth).

- טקסט משני/מטא: כ-13 פיקסלים, צבע טקסט משני.

**8.4 מרווחים ופריסה (Grid & Spacing)**

- סולם מרווחים בסיסי של 8 פיקסלים (8 / 16 / 24 / 32)
  לעקביות מלאה בכל האפליקציה.

- רוחב תוכן מרבי (Container): כ-1200 פיקסלים במסכים
  רחבים, ממורכז, עם רווחי צד (Padding) הולכים וקטנים ככל שהמסך
  מצטמצם.

- נקודות שבירה רספונסיביות (Breakpoints): מובייל עד 600
  פיקסלים, טאבלט 600–960 פיקסלים, דסקטופ מעל 960 פיקסלים.

**8.5 אייקונוגרפיה**

שימוש עקבי בסט Material Icons (או Material Symbols) בכל
האפליקציה — אייקון ייעודי לכל קטגוריה (למשל תג מחיר לקטגוריית מכירה,
מפתח לדיור להשכרה, כרטיס כניסה לאירועים, מזוודה לטיולים), וכן אייקונים
תפקודיים אחידים (חיפוש, מיקום, עריכה, מחיקה, סגירה).

**8.6 מצבי רכיב (States)**

- Hover — הצללה עדינה/הבהרה קלה בכל אלמנט לחיץ.

- Active/Selected — מסגרת או רקע בצבע ה-Primary, לדוגמה
  על תגית קטגוריה נבחרת.

- Disabled — שקיפות מופחתת (כ-40%) ומצביע עכבר "אסור",
  למשל בכפתור שמירה בטופס לא תקין.

- Error — מסגרת/טקסט באדום מתחת לשדה טופס שגוי, עם הודעת
  שגיאה מפורשת וברורה.

**8.7 כיווניות (RTL)**

כל האפליקציה מתוכננת ונבנית כתצוגת RTL מלאה כברירת מחדל
(תגית ה-HTML הראשית מוגדרת dir="rtl" lang="he"), כולל היפוך מלא של:
כיוון קריאה, יישור טקסט, מיקום אייקונים (חצים, אייקוני חזרה), כיוון
תפריטים נפתחים ודיאלוגים, וסדר עמודות בכל טבלה או רשת. שילוב ה-Google
Maps (הפועל באופן טבעי LTR פנימית במפה עצמה) מטופל כך שהאלמנטים הסובבים
אותו (שדה חיפוש כתובת, כפתורים) נשארים RTL עקביים עם שאר הממשק.

**9. דרישות לא פונקציונליות**

**9.1 רספונסיביות**

האפליקציה נבנית בגישת Mobile-First ונבדקת בשלושה גדלי
מסך עיקריים: מובייל, טאבלט ודסקטופ (ראו נקודות שבירה בסעיף 8.4). כל מסך,
טופס ורכיב (כולל המפה) חייב להישאר שמיש ונוח לחלוטין גם ברוחב מסך
צר.

**9.2 נגישות (Accessibility)**

- ניגודיות צבעים עומדת בסטנדרט WCAG AA לפחות עבור טקסט
  מול רקע.

- כל רכיב אינטראקטיבי (כפתור, שדה, כרטיס לחיץ) נגיש גם
  בניווט מקלדת (Tab / Enter) ונושא תיוג ARIA מתאים לקוראי מסך.

- תמונות נושאות טקסט חלופי (alt) מבוסס כותרת
  המודעה.

**9.3 ביצועים**

- טעינה עצלה (Lazy Loading) של תמונות ברשת
  המודעות.

- שימוש באסטרטגיית זיהוי שינויים OnPush ברכיבי Angular
  מרכזיים לצמצום עיבודים מיותרים.

- השהיה (Debounce) על שדה החיפוש כדי לא להציף את השרת
  בבקשות בכל הקשה.

- עימוד תוצאות בצד השרת כדי לשמור על זמני תגובה קצרים גם
  עם מספר רב של מודעות.

**9.4 טיפול בשגיאות רשת**

כל כשל תקשורת מול השרת (זמן קצוב, שרת לא זמין, שגיאת
שרת) מוצג למשתמש כהודעה ברורה וידידותית (לא קוד שגיאה טכני), עם אפשרות
"נסה שוב" במקומות הרלוונטיים (בעיקר בטעינת הרשימה הראשית).

**9.5 תאימות דפדפנים**

תמיכה מלאה בגרסאות עדכניות של Chrome, Edge ו-Firefox.
שירות המיקום הגיאוגרפי (Geolocation) דורש הרשאת דפדפן ופועל רק בהקשר
מאובטח (HTTPS או localhost).

**9.6 אבטחה בסיסית**

- סניטציה של קלט טקסטואלי חופשי (כותרת, תיאור) למניעת
  הזרקת קוד (XSS) — הן בהצגה בצד הקליינט (הימנעות משימוש ב-innerHTML
  גולמי) והן בבדיקת קלט בצד השרת.

- ולידציה מלאה בצד השרת בכל נקודות הקצה, ללא הסתמכות
  בלעדית על ולידציית הקליינט הניתנת לעקיפה.

- הגבלת גודל וסוג קובץ תמונה מותרים להעלאה, הן בקליינט
  והן בשרת.

- מפתח ה-Google Maps API אינו נכתב ישירות במאגר הקוד
  הציבורי, ומוגבל בקונסולת Google Cloud לדומיין/כתובות המורשות בלבד (ראו
  סעיף 11).

**11. מבנה הפרויקט ב-GitHub ודרישות מסירה**

**11.1 מבנה תיקיות מוצע במאגר**

- **/client —** פרויקט ה-Angular במלואו.

- **/server —** פרויקט ה-ASP.NET Core Web API במלואו,
  כולל קובץ ה-ads.json (עם נתוני seed בלבד, ללא נתונים אישיים
  כלשהם).

- **/docs —** צילומי מסך של האפליקציה הרצה, ותרשימים
  תומכים (אופציונלי).

- **README.md —** בשורש המאגר.

- **.gitignore —** בשורש המאגר, מוציא מהמעקב תיקיות
  התקנה (node_modules, bin, obj), קבצי סביבה רגישים וקבצי בנייה.

**11.2 תוכן קובץ README נדרש**

**1.** תיאור קצר של הפרויקט ומטרתו.

**2.** רשימת הטכנולוגיות בהן נעשה שימוש (Angular,
Angular Material, C#/ASP.NET Core וכו').

**3.** הוראות הרצה מלאות ומדויקות עבור צד השרת (כולל
דרישת גרסת .NET) וצד הקליינט (כולל דרישת גרסת Node.js), משלב שכפול המאגר
ועד לצפייה באפליקציה רצה בדפדפן.

**4.** רשימת משתני סביבה/מפתחות נדרשים (בפרט מפתח Google
Maps API) והסבר היכן להגדיר אותם מקומית מבלי לחשוף אותם ב-Git.

**5.** צילומי מסך מייצגים של המסכים המרכזיים (לוח
מודעות, פרטי מודעה, טופס יצירה עם מפה).

**11.3 טיפול במפתח Google Maps API**

מפתח ה-API אינו נכתב בקוד המחובר ל-Git. במקום זאת: קובץ
סביבה מקומי (למשל environment.local.ts) הכולל את המפתח האמיתי מתווסף
ל-.gitignore ואינו נדחף למאגר; לצידו נשמר ונדחף למאגר קובץ תבנית לדוגמה
(למשל environment.template.ts) עם placeholder בלבד, ומוסבר ב-README כיצד
להעתיקו ולמלא בו מפתח אישי. בנוסף, מומלץ להגביל את המפתח בקונסולת Google
Cloud כך שישמש אך ורק מהדומיינים/הכתובות המורשים (localhost בסביבת
פיתוח, ודומיין הפריסה בסביבת ייצור, אם קיימת).

**11.4 מסירת הפרויקט**

בסיום העבודה, המאגר ב-GitHub נדחף במלואו (Push) לענף
הראשי, ונשלח קישור (Link) ישיר למאגר לגורם המבקש — כפי שנדרש במפורש
במסמך המשימה המקורי.
